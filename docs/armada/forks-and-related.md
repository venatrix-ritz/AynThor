# Armada forks and related community projects
> Scope: the three extra git remotes in `refs/upstream/armada` (SilentBob347, Ga1dz1, MgeeeeK), the virtudude → armada-os rename, and other community OS projects that overlap Armada/Thor · Researched: 2026-10-03 · Confidence: high for fork contents (read from git), medium for "why" (commit text only)

## Summary
- **MgeeeeK/thor-armada** is the only fork that is Thor-specific. It is 5 commits on top of upstream (merge-base 2026-09-13), adds a fixed 80% charge-limit service for the Thor, and pins a kernel package built from a second fork (`MgeeeeK/armada-packages`) that adds SDR104 microSD support and three `qcom_battmgr` patches. Four of the five commits and the kernel commit carry `Claude-Session:` trailers, i.e. they are AI-assisted.
- **Ga1dz1/armada** is *not* a Thor fork. It is a Retroid Pocket (SM8250, "Snapdragon 865") fork with 116 commits, archived 2026-08-22/23 because it diverged and continues as a standalone project, **Nebel** (`Ga1dz1/nebel`). Its only Thor touch-point is a shared InputPlumber change that the author flags as unverified on Thor hardware.
- **SilentBob347/armada-os** has zero commits of its own. Every commit on every branch is by upstream's maintainer ("virtudude") or dependabot. It is a passive snapshot of upstream branches (main frozen at 2026-08-17).
- **virtudude/armada** is a redirect: `gh api repos/virtudude/armada --jq .full_name` returns `armada-os/armada`.
- Upstream `main` (574da80) has since added, in part, what the forks were made for: Thor Lite (SM8250) device files, a `constant_charge_current` exposure of the same firmware property the MgeeeeK fork exposes as `charge_control_limit`, and removal of `sdhci-caps-mask` from the AYN common DTSI.

**Userspace charge limit** (`/usr/libexec/armada/thor-charge-limit`, bash, "No configuration"): [src: refs/upstream/armada@7e17352:system_files/usr/libexec/armada/thor-charge-limit#L1-L29]
1. Waits up to 120 s for `/sys/class/power_supply/battery/charge_control_limit`, `/sys/class/power_supply/qcom-battmgr-usb/online` and `capacity`; exits 1 with "patched qcom_battmgr not loaded?" if the limit file never appears.
2. At start writes `80` to `battery/charge_control_end_threshold` (script comment: "AYN firmware capacity-limit flag, property 16").
3. Every 30 s: on charger (`qcom-battmgr-usb/online` = 1) and `capacity` >= 80, "clamp" by writing `1000` (script comment: uA) to `charge_control_limit`; `capacity` <= 77 or charger removed, "release" by writing `charge_control_limit_max` back (fallback 9000000). Hysteresis 77 to 80.
4. If on charger at <= 77% in the released state but `status` is not Charging, every 10th consecutive 30-s poll (about 5 min) it logs an error and re-sends the max value.
5. A TERM/INT trap and `ExecStopPost` in the unit release the clamp; `Restart=always`, `RestartSec=10`. [src: refs/upstream/armada@7e17352:system_files/usr/lib/systemd/system/thor-charge-limit.service#L1-L13]
6. The system-sleep hook, on `pre` while on charger with capacity >= 70, writes `1000` to `charge_control_limit`; on `post` it restarts the service. It exits 0 if `charge_control_limit` does not exist. [src: refs/upstream/armada@7e17352:system_files/usr/lib/systemd/system-sleep/60-thor-charge-limit#L1-L9]

Since the "clamp" is a 1000-unit charge-current limit rather than a hard stop, and the firmware capacity flag (property 16) is also set at start, which of the two actually holds the battery near 80% on hardware is [UNVERIFIED — no device access; the kernel patch text only says the firmware accepts SET property 16].
