## Technical takeaways
- Android apps treat the Thor as **two `Display`s** enumerated through `DisplayManager` (auto-dim service watches display add/remove/change and picks the secondary). [src: refs/thor-android/ayn-thor-auto-dim@b7f10cc:app/src/main/kotlin/com/jeromegsq/aynthorautodim/DimmingService.kt#L78-L141]
- Third-party Android tooling (Wayfinder) works without root on stock firmware, implying AYN exposes enough (settings/accessibility APIs) for per-app screen placement [UNVERIFIED mechanism — source not read].
- Tools key off **specific stock firmware builds** (Wi-Fi recovery fails closed on anything but `.377`), so stock updates can break them. [src: refs/thor-android/AYN-Thor-WiFi-Recovery@2144afb:README.md]
- **Cocoon** (formerly CocoonFE) is hosted at `inssekt/CocoonFE` (cocoon-shell.com). It is a popular emulation frontend for Android with dual-screen support ("Now Playing" on the second screen). [src: WebSearch 2026-10-03]

### Install status on Ven's Thor (2026-10-04; clones in `refs/community/`)
- **thor-armada-audio-fix: installed by Ven** — `jamesdsp-auto` user service active, `me.timschneeberger.jdsp4linux` 2.7.0 flatpak present, `~/.config/jdspthorfix/speaker_daemon.sh` present. Whether a preset is actually being applied was not verified. [observed]
- **barry-launcher: blocked by missing prerequisites** — on the Thor `qml-qt6`/`qml6`/`/usr/lib64/qt6/bin/qml` and `xdotool` are **missing**; `xprop`, `python3`+AT-SPI, `firefox`, `flatpak`, `vulkaninfo` are present; gamescope supports `--drm-lease-client` and runs with `--lease-connector`. `install.sh` only *warns* about a missing QML runner ("nothing will draw"), and needs `sudo` for a udev rule plus an InputPlumber override for the AYN button. Armada's root is an immutable bootc image, so adding Qt6 qml/xdotool needs a layering/overlay step that was not researched. [observed] [src: refs/community/barry-launcher@13ab555:install.sh#L96-L115]
- **Update 2026-10-04 — `Lossless.dll` copied to the Thor:** Ven bought Lossless Scaling but could not install it through Steam on the Thor, so the DLL was copied from the PC (`F:\Steam\steamapps\common\Lossless Scaling\Lossless.dll`, 7 521 280 B) to `~/.local/share/Steam/steamapps/common/Lossless Scaling/Lossless.dll`; SHA-256 `626b196d…19f0eb` matches on both ends. That path is exactly what `armada-lsfg-adaptive` (`py_modules/lsfg/steam.py#L185-L188`: `<library>/steamapps/common/Lossless Scaling/Lossless.dll`) and `lsfg-vk-odin2-armada`'s `install.sh` (`find ~/.steam ~/.local/share/Steam -name Lossless.dll`) search; the plugin does not need an appmanifest for the DLL lookup. [observed] [src: refs/community/armada-lsfg-adaptive:py_modules/lsfg/steam.py] **Vetting:** `armada-lsfg-adaptive/install.sh` downloads the GitHub release zip (v0.2.2, 489 KB, only release day 2026-08-17, 0★), verifies its published `.sha256`, backs up any existing copy, places it in `~/homebrew/plugins/ArmadaLSFGAdaptive` (sudo only if root-owned) and restarts `plugin_loader`; the aarch64 layer is installed at user level from inside the plugin. `lsfg-vk-odin2-armada/install.sh` is user-level only (no sudo/network) but its README's published `install.sh` SHA-256 (`5bab0e2a…`) **does not match** the cloned file (`9f0d22f5…`) — stale checksum or changed script, unresolved. Both ship prebuilt `.so` layers whose build I could not verify against source.
- **`armada-lsfg-adaptive` installer failure (2026-10-04, Ven ran `curl | bash` on the Thor):** it printed "checksum mismatch". Cause established from the release assets: the zip's real SHA-256 (`6d0a6cae…32bb`) **equals** the hash in the published `.sha256`, but that file lists the path `out/ArmadaLSFGAdaptive-0.2.2.zip`, so `sha256sum --check` (run in the temp dir) cannot open it, and the script's fallback `shasum` does not exist on Armada ("shasum: command not found") → it reports a mismatch. A packaging bug upstream, not corruption. Zip contents: Decky plugin (JS + Python) plus two prebuilt aarch64 binaries, `bin/liblsfg-vk-layer.so` (650 792 B, layer `git-8b0da2661c6f`, differs from the Odin 2 repo's layer) and `bin/lsfg-vk-cli` (580 024 B); the installer's own validation rejects symlinks/unsafe paths. A manual verified install was proposed instead; pushing a patched installer to the Thor was blocked by the harness and left to Ven. [src: GitHub release v0.2.2 assets, downloaded to scratchpad for inspection] [observed: installer output pasted by Ven]
- **State after Ven's manual install (2026-10-04, read-only check):** `ArmadaLSFGAdaptive` v0.2.2 is in `~/homebrew/plugins` (root-owned), its bundled `liblsfg-vk-layer.so` hash equals the zip's, `plugin_loader` is active and is reading the plugin's files. **"Engine lacks adaptive mode" is real:** `bin/layer-info.json` of v0.2.0–v0.2.2 says `source: upstream`, `adaptive: false` (layer `git-8b0da2661c6f`, built with Dockerfile default `LSFG_SOURCE=upstream`), and the plugin gates adaptive on `capabilities.adaptive` (`main.py#L226-L233`); only v0.1.0–v0.1.5 bundle the experimental engine (`2.0.0-dev28-experimental.25`, `adaptive: true`); the README still describes the experimental engine. v0.1.5 zip SHA-256 `07c91d26…dc29` (369 413 B; its `.sha256` has the same `out/` path bug). Fixed-multiplier mode works without adaptive. **Pre-existing LSFG setup:** a second plugin `Decky LSFG-VK` is installed, with its own user-level layer (`~/.local/lib/liblsfg-vk.so`, 3 MB, Oct 2 19:58), the same layer manifest name `VK_LAYER_LSFGVK_frame_generation.json`, and `~/.config/lsfg-vk/conf.toml` (profile `decky-lsfg-vk`, multiplier 2, flow_scale 0.8, performance_mode false, `dll` = the lsfg-vk default `/games/Lossless Scaling/Lossless.dll`, which does not exist on the Thor). Two plugins share one layer name and one `conf.toml`; the new plugin's "Install LSFG" would replace that manifest. [observed]
- **barry-launcher installed in user space (2026-10-04):** The prerequisite packages (`libxdo`, `xdotool`, `qt6-qtdeclarative-devel` for `qml-qt6`) were missing from Armada's read-only root. Instead of transient `bootc usroverlay` or risky `rpm-ostree`, Fedora 44 aarch64 RPMs were downloaded and extracted cleanly to `~/.local/opt/barry-deps/`. Wrapper scripts placed in `~/.local/bin/{xdotool, qml-qt6}` set `LD_LIBRARY_PATH` to the extracted `usr/lib64`. Verified on device: `xdotool` and `qml-qt6` work perfectly. The full `barry-launcher` install script was then executed: it installed the user services (`barry_launcher.service`, `barry_launcher_inputd.service`), tied them to `gamescope-session-plus@steam.service`, added a udev rule for `uinput`, and installed an `InputPlumber` override to release the AYN button. A device reboot is required for the InputPlumber override to take effect. [observed]
- **Update 2026-10-04 — `conf.toml` DLL path configured:** The active `~/.config/lsfg-vk/conf.toml` had a default dummy path (`/games/Lossless Scaling/Lossless.dll`). It was updated to point directly to the verified DLL copied to `~/.local/share/Steam/steamapps/common/Lossless Scaling/Lossless.dll` (`/var/home/armada/.local/share/Steam/steamapps/common/Lossless Scaling/Lossless.dll`), with a backup saved at `conf.toml.bak-before-dll-fix`. [observed]
- **MgeeeeK/thor-armada image: not applicable as an add-on.** It is a full replacement OS image (`ghcr.io/mgeeeek/thor-armada`) whose commits add its own cosign key + `policy.json`; switching to it from the stock image means making the device trust a new third-party signing key for the whole root filesystem. Its charge-limit script needs `charge_control_limit`/`_limit_max` nodes from the fork's patched `qcom_battmgr`, which the stock kernel does not expose (the stock kernel has `charge_control_end_threshold`, currently 0, and `constant_charge_current` = 9 000 000 µA). [src: refs/upstream/armada@7e17352 (fork diff)] [observed]
