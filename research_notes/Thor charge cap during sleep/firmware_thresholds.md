# Firmware- and kernel-level charge limiting on qcom_battmgr (pmic_glink), AYN Thor (SM8550, Armada OS, kernel 7.2.6)

Research date: 2026-10-08. Scope: can any firmware- or kernel-held mechanism hold an 80 % cap with nothing running in userspace during suspend, and why do `charge_control_end_threshold` writes on the Thor succeed but read back 0 with no effect.

**Tags.** `[V]` verified in source this turn (file, SHA and line, or a raw page read). `[S]` secondary (forum, issue, README, fork author's claim, or a page reached only through a summariser). `[U]` unverified: inference or open question.

**Local sources read (SHAs):** `refs/upstream/armada@574da80`, `refs/upstream/armada-packages@f02c7c8`, `refs/upstream/rocknix@9f8c79d`, `refs/thor-android/thor-wayfinder@305d3ad`, `refs/thor-android/android_device_ayn_qcs8550-common@d5e669d`, `refs/thor-android/android_kernel_ayn_qcs8550-devicetrees@9b2d195`, `refs/thor-linux/ayn-thor-arch@84aba0a`, `refs/_gh/` exports. **Remote sources read:** torvalds/linux at `6c377d19d4a5` (2026-10-08, `drivers/power/supply/qcom_battmgr.c`, 1746 lines; Linux v7.2.6 differs from it only at the chemistry `strncmp` lines 1241-1245, so the line numbers below hold for Armada's base before its 090x patches), NothingOSS `android_kernel_msm-6.1_nothing_sm7635@d5f5f96` (a downstream QTI kernel, not AYN's), msmirle/nova-charge-limiter `aa69f28`, MgeeeeK/armada-packages `thor@4c2c000`, lkml.iu.edu mirrors of lore threads.

Local facts taken as given and not re-derived: `constant_charge_current` = 0 stops charging and holds across s2idle while clamped; `charge_control_{start,end}_threshold` exist, a write of 80/90 succeeds, reads back 0, changes nothing (2026-10-07, 2026-10-08).

## Objective: is there a firmware- or kernel-held 80 % cap that works with nothing in userspace during suspend, and why does the threshold read back 0?

### Takeaway
No mechanism that stops charging at 80 % during s2idle is known to work on this Thor firmware. The mainline threshold path (opcode 0x48) is accepted by the driver but the Thor's ADSP firmware shows no sign of implementing it; the readback of 0 is the firmware's own answer to a GET, not a stored copy of what was written. Two untested candidates remain: AYN's own firmware flag `limit_capacity_charge` (present in the Thor's ADSP binary, used by AYN's Android) and a kernel-side power-supply notifier.

### Cited Findings
- The Thor's `adsp.mbn` (the file Armada loads) contains the AYN-specific strings `battmngr_plat_scpqchg_qbg_r1_charger_config:: usb_charge_now=%d, limit_capacity_charge=%d, bat_capacity = %d curr_cap_state = %d, last_cap_state = %d` and `limit_capacity_charge %d != last_limit_capacity_charge %d!`, but not the strings `battmngr_set_charging_limit::enable = %d, target soc = %d, delta soc = %d` or `charge_limit_config = %d, enabled`, which the Odin 3 (SM8750), KONKR Pocket Fit Elite (SM8750) and AYANEO PS2 (SM8650) blobs in the same tree do contain. [V] `refs/upstream/armada@574da80:system_files/usr/lib/firmware/qcom/sm8550/ayn/thor/adsp.mbn` (sha256 `e771ab967310…`, string offsets 0xc7358f / 0xc73639; no `set_charging_limit` string anywhere in the file); `…/sm8750/ayn/odin3/adsp.mbn` (0x70a79d, 0x6aef7d); `…/sm8750/konkr/pfe/adsp.mbn` (0x70509e); `…/sm8650/ayaneo/ps2/adsp.mbn` (0x6e69b8, 0x69513d). Found by byte-level string search this turn.
- The Odin 2, Odin 2 Mini and Odin 2 Portal blobs contain neither the `limit_capacity_charge` nor the `set_charging_limit` strings; the Retroid Pocket 6 blob has the Thor's `limit_capacity_charge` strings and no `set_charging_limit`. [V] same directory, `sm8550/ayn/odin2*/adsp.mbn`, `sm8550/retroidpocket/rp6/adsp.mbn` (0xc75639).
- Mainline's threshold request sends opcode `BATTMGR_CHG_CTRL_LIMIT_EN` (0x48) with enable=1, target_soc, delta_soc; the Odin 3 / PS2 / PFE firmware strings show a handler that logs exactly those three fields. [V] `torvalds/linux@6c377d19d4a5:drivers/power/supply/qcom_battmgr.c#L662-L675` ([link](https://github.com/torvalds/linux/blob/6c377d19d4a5116d9bec5203aa3c6c11523e7898/drivers/power/supply/qcom_battmgr.c#L662-L675)); firmware strings above.
- The Android "Stop at 80 %" setting `percent_80_charge_limit` is written by AYN to `/sys/class/qcom-battery/limit_capacity_charge`; "Direct power" (`is_charging_separation`) goes to `usb_charge_now`. The limit stops charging at 80 % and does not discharge a fuller battery. Verified on a Thor by the app author (2026-10-01). [S] `refs/thor-android/thor-wayfinder@305d3ad:app/src/main/java/app/wayfinder/Charging.kt#L10-L22`. The strings `usb_charge_now` and `limit_capacity_charge` in the Thor firmware match these two node names. [V] firmware offsets above.
- A Thor in suspend is not a dead ADSP: Armada's commit message says the ADSP charger firmware pushes an unsolicited `BATTMGR_NOTIFICATION` about 0.5 s after suspend entry, and patch 0504 keeps the IPCC doorbell live in suspend-to-idle ("a live doorbell lets the charger firmware complete a cable attach with the AP asleep") while masking it only for suspend-to-RAM. [V] `refs/upstream/armada@574da80` git commit `ee66da0` (2026-08-05, message body); `refs/upstream/armada@574da80:packages/kernel/patches/0504-mailbox-qcom-ipcc-mask-summary-irq-for-suspend-to-ram.patch#L1-L22`. These are the patch author's statements, not independently measured.
- The only state-holding control known to work on the Thor is `constant_charge_current` (BATT_CHG_CTRL_LIM, prop 10). It is a plain on/off current clamp that needs something to flip it at 80 %. [V] `refs/upstream/armada@574da80:packages/kernel/patches/0903-power-supply-qcom-battmgr-expose-the-charge-current-limit.patch#L1-L8`; clamp reaching 0 A within about 5 s measured 2026-10-08, `docs/hardware/device-observed.md#L89-L92` (local observation).
- Battery-charge pause holding through real sleep is also asserted for the Retroid Pocket Nova, along with the statement that nothing flips it at 80 % while asleep, and the observation that a firmware-threshold build let the Nova charge from 69 % to 96 % asleep. [S] `msmirle/nova-charge-limiter@aa69f28:README.md#L141-L152` ([link](https://github.com/msmirle/nova-charge-limiter/blob/aa69f2896e3304396a8a4de86dc391df8f9a8394/README.md)).

### Inferences
- The Thor ADSP binary appears to lack the mainline charge-limit handler and to carry an AYN-specific alternative. String absence is circumstantial (a handler can exist without a log line) but the contrast with three sibling blobs that do log it is the strongest evidence found. [U]
- If the `limit_capacity_charge` state machine runs inside the firmware (it is in `…charger_config`, next to `curr_cap_state/last_cap_state`), then once the flag is set the 80 % hold would not need the AP. That it actually stops charging at 80 % and survives s2idle on the Thor has not been shown by anyone found here. [U]
- A kernel-held fallback (a `power_supply_reg_notifier` in `qcom_battmgr` that writes prop 10 = 0 on a battery event, like patch 0532 does for the fan) is feasible only if the firmware keeps sending battery/SoC events during s2idle and the callback runs while the AP is idle. Evidence for the first half is the 0.5 s doorbell; neither half was observed. [U]

### Gaps
- Which pmic_glink property ID sets `limit_capacity_charge` from Linux. Only the MgeeeeK fork claims one (16), see Q4; never confirmed by a test that charging stopped.
- Whether `limit_capacity_charge` fixes an SoC (80) or something else, and whether the firmware applies it while the AP is in s2idle.
- No source found for any Snapdragon handheld whose firmware threshold was shown to hold through s2idle.

## Q1. What do the mainline git history and lore threads say about which SoCs/firmware implement BATTMGR_CHG_CTRL_LIMIT_EN, who wrote it, and where was it tested?

### Takeaway
Fenglin Wu of Qualcomm wrote the feature (commit `cc3e883a0625`, 2025-09-17) and says the SM8550 and X1E80100 platforms "now include" charge control in their battery management firmware. It was tested on a QRD8650 (SM8650), an X1E80100 CRD and a ThinkPad T14s OLED, never on an OEM SM8550 handheld. Nothing in the threads says which SM8550 firmware builds implement it.

### Cited Findings
- Author and commit: `cc3e883a0625` "power: supply: qcom_battmgr: Add charge control support", Fenglin Wu, 2025-09-17, `Tested-by: Neil Armstrong # on Thinkpad T14S OLED`, merged by Sebastian Reichel; the commit text covers only the two properties. [V] [commit](https://github.com/torvalds/linux/commit/cc3e883a06251ba835f15672dbe8724f2687971b); same text in [v5 7/9](https://lkml.iu.edu/2509.2/02367.html).
- Firmware claim: `b3c0f651b3cf` "update compats for SM8550 and X1E80100" says "The SM8550 and X1E80100 platforms now include charge control functionality in battery management firmware, allowing charging to stop when the battery reaches a set level and resume when it drops below another level." [V] [commit](https://github.com/torvalds/linux/commit/b3c0f651b3cf4dfaf2e8210d7bb9b79471f6403b); [v5 5/9](https://lkml.iu.edu/2509.2/02366.html).
- Cover letter (v3-v5): "The changes have been tested on QRD8650 and X1E80100-CRD devices" and the series was written "as the battery management firmware has provided such capabilities". Neil Armstrong's reply adds "Gnome sets the properties and they are correctly loaded back at reboot" on the T14s OLED. [V] [v3 thread, Neil Armstrong 2025-09-03](https://lkml.iu.edu/hypermail/linux/kernel/2509.0/04320.html); [v5 cover](https://lkml.iu.edu/2509.2/02361.html).
- The QRD8650 is an SM8650 board whose DT lists `"qcom,sm8650-pmic-glink", "qcom,sm8550-pmic-glink", "qcom,pmic-glink"`, so the SM8550 variant of the driver was what ran there; the driver's match table maps `qcom,sm8550-pmic-glink` to `QCOM_BATTMGR_SM8550`. [V] `torvalds/linux@6c377d19d4a5:arch/arm64/boot/dts/qcom/sm8650-qrd.dts#L50-L52`; `drivers/power/supply/qcom_battmgr.c#L1616-L1621` ([link](https://github.com/torvalds/linux/blob/6c377d19d4a5116d9bec5203aa3c6c11523e7898/drivers/power/supply/qcom_battmgr.c#L1616-L1621)).
- v3 changelog: X1E80100 firmware has "no interface to retrieve the thresholds from the battery management firmware after boot-up", so the driver reads them from PMIC SDAM nvmem cells at probe (`charge_limit_en/end/delta`). [V] [v3 cover](https://lkml.iu.edu/hypermail/linux/kernel/2509.0/04320.html); binding in [v5 6/9](https://lkml.iu.edu/2509.2/02360.html). Only `x1-crd.dtsi` (cells defined in `hamoa-pmics.dtsi`, `pmk8550_sdam_15` offsets 0x73/0x75/0x76) uses these cells in mainline; the SM8550/SM8650 boards (`sm8550-hdk/mtp/qrd`, `sm8650-qrd/mtp/hdk`, …) carry none. [V] `torvalds/linux@6c377d19d4a5:arch/arm64/boot/dts/qcom/x1-crd.dtsi#L85-L90`, `hamoa-pmics.dtsi#L245-L262`; `rg charge_limit_en arch Documentation` returns only those files plus the binding.
- Dmitry Baryshkov asked twice why SM8550 and X1E80100 must be handled differently; the reply only points to the commit text and the bisectability request. The thread does not state the SM8550 firmware difference. [V] [v4 5/8 thread](https://lkml.iu.edu/2509.2/00457.html).
- Later history: `41307ec7df05` (0x83 charging-state notifications; bit 8 of the code is set "when charging stops because the charge control end threshold is reached"); `8809980fdc8a` Val Packett, clamp thresholds; `446fcf494691` Val Packett, support disabling (start=0 sets enable=0); `8e8856396b54` Sebastian Reichel reverts it on 2025-11-03; `16a7c32e586e` (2026-02-09) adds the `kaanapali-pmic-glink` compatible as `QCOM_BATTMGR_SM8550`. [V] [41307ec](https://github.com/torvalds/linux/commit/41307ec7df057239aae3d0f089cc35a0d735cdf8), [8809980](https://github.com/torvalds/linux/commit/8809980fdc8a86070667032fa4005ee83f1c62f3), [446fcf4](https://github.com/torvalds/linux/commit/446fcf494691da4e685923e5fad02b163955fc0e), [8e88563](https://github.com/torvalds/linux/commit/8e8856396b54bea5c00a7ae88d87c6254aef2d94), [16a7c32](https://github.com/torvalds/linux/commit/16a7c32e586ed9c7e1bbaac7c441afcf474a67bb).

The 50 % start floor is a UX choice. [V] [Fenglin Wu, 2025-11-17](https://lkml.iu.edu/2511.2/02578.html) (raw page read); also [Konrad Dybcio's quote of it](https://lkml.iu.edu/2511.2/03172.html).
- Kernel Documentation: drivers "round written values to the nearest supported value. Reading back the value will show the actual threshold set by the driver." [V] `torvalds/linux@6c377d19d4a5:Documentation/ABI/testing/sysfs-class-power#L362-L372`.

### Inferences
- The SM8550 variant has been exercised on Qualcomm reference firmware (SM8650 QRD) and the commit text speaks of SM8550 firmware "now" including it, which reads as a firmware-release dependency; the threads do not name a version. [U]
- On the X1E80100 the thresholds persist in PMIC SDAM across reboots and the firmware enforces them without Linux (the 0x83 notification bit says the firmware stopped charging at the threshold). That is the nearest documented analogue of the "no userspace in suspend" requirement, but no source tests it across suspend. [U]

- Val Packett's IRC discussion is not archived; the nature of the "strange" disable bit is unknown.

## Q2. Does the kernel log a failure when the request is rejected, and what makes the readback 0?

### Takeaway
Mainline logs nothing when the threshold request fails: every failure path is swallowed and the sysfs write returns success. On the SM8550 variant each read of `charge_control_end_threshold` issues a fresh GET of firmware property 26 and overwrites the cached value with the firmware's answer, so a readback of 0 means the firmware answered 0; it says nothing about whether the SET worked.

### Cited Findings
- `qcom_battmgr_set_charge_end_threshold()` and the start variant return 0 unconditionally, caching the new value only when the request returned 0. [V] `torvalds/linux@6c377d19d4a5:drivers/power/supply/qcom_battmgr.c#L677-L728` ([link](https://github.com/torvalds/linux/blob/6c377d19d4a5116d9bec5203aa3c6c11523e7898/drivers/power/supply/qcom_battmgr.c#L677-L728)).
- A request waits `wait_for_completion_timeout(…, HZ)` and returns `-ETIMEDOUT` after 1 s with no log line; otherwise it returns `battmgr->error`. [V] same file `#L344-L362`.
- The 0x48 reply case sets `battmgr->error = 0` without reading any result field, and an unknown opcode only produces a `dev_warn("unknown message %#x")` before completing the wait with error still 0. [V] same file `#L1559-L1569` (SM8350/SM8550 callback; the SC8280XP/X1E callback does the same at `#L1355-L1357`). A reply shorter than 4 payload bytes logs "invalid payload length" and returns without completing, which also ends in the 1 s timeout (`#L1375-L1380`).
- So the logged cases are only "unknown message", "invalid payload length" and "unknown property" warnings; a timeout, a firmware reply that ignores the request, or a firmware reply that carries an error all produce zero log lines and a successful write. [V] same file as above; no `dev_err` exists on the set path.
- For `QCOM_BATTMGR_SM8550`, `get_property` dispatches to `qcom_battmgr_bat_sm8350_update()`, which sends `BATTMGR_BAT_PROPERTY_GET` for the property mapped from the psp: prop 25 for START and prop 26 for END. Only SC8280XP and X1E80100 take the other update path. [V] same file `#L451-L452`, `#L455-L470`, `#L523-L527`.
- The GET callback checks `intval.result`; a non-zero result sets `battmgr->error` and jumps to `out_complete`, so the sysfs read would then fail with that error. Otherwise it stores the reply value into `info.charge_ctrl_start/end`, overwriting whatever the driver cached after the SET. [V] same file `#L1400-L1405`, `#L1472-L1476`. `get_property` then reports `info.charge_ctrl_end`, `#L631-L636`.
- X1E80100 never GETs these properties: its readback is the cache seeded from SDAM at probe plus the last successful SET, which is why a T14s "loads back at reboot" says nothing about SM8550 readback. [V] same file `#L731-L757`, `#L1661`, `#L523-L525`.
- The Thor's DT uses `"qcom,sm8550-pmic-glink", "qcom,pmic-glink"` and carries no `nvmem-cells`, so `thresholds_init()` does nothing and the cache starts at 0. [V] `refs/upstream/armada@574da80:packages/kernel/dts/qcs8550-ayn-common.dtsi#L58-L59`; `rg nvmem` on that file shows only RTC/haptics cells.
- Armada's `BATT_CHG_CTRL_LIM` patch adds a `BATTMGR_BAT_PROPERTY_SET` case that parses `intval.result` (−EIO on non-zero) because mainline's SM8350 callback has no case for the 0x31 reply. [V] `refs/upstream/armada@574da80:packages/kernel/patches/0903-power-supply-qcom-battmgr-expose-the-charge-current-limit.patch#L109-L120`. No Armada patch touches the threshold set path or adds logging there. [V] `rg -i 'charge_control|threshold' packages/kernel/patches/09*` finds only 0903's `CONSTANT_CHARGE_CURRENT` code; `PATCHES.md#L389-L402` lists 0900-0903 only.
- Mainline defines `BATT_CHG_CTRL_EN` (property 24) but never reads or writes it. [V] `torvalds/linux@6c377d19d4a5:drivers/power/supply/qcom_battmgr.c#L74` is the only occurrence. The QTI downstream driver gates every threshold write on it: `if (!bcdev->chg_ctrl_en) return 0;`, with the flag read from the firmware at probe and exposed as the class attribute `charge_control_en`. [V] `NothingOSS/android_kernel_msm-6.1_nothing_sm7635@d5f5f96:drivers/power/supply/qti_battery_charger.c#L2969-L2970, #L3048-L3061, #L3721-L3761, #L4468` ([file](https://github.com/NothingOSS/android_kernel_msm-6.1_nothing_sm7635/blob/d5f5f965fd0b478eaf4eb63fd984c5a4a92135a7/drivers/power/supply/qti_battery_charger.c)). That is a Nothing (SM7635) tree, not AYN's.
- Local observation: write 80, readback 0, no effect; the previously deployed unit logged "readback=0" and still reported success. [V, local] `docs/hardware/device-observed.md#L75`; `#L33`.
- MgeeeeK's fork author states that on the AYN SM8550 firmware GETs of properties 25/26 "always return 0". [S, low confidence, single AI-assisted author] `MgeeeeK/armada-packages@4c2c000:kernel/patches/0922-power-supply-qcom-battmgr-sm8550-threshold-getter.patch` ([raw](https://raw.githubusercontent.com/MgeeeeK/armada-packages/thor/kernel/patches/0922-power-supply-qcom-battmgr-sm8550-threshold-getter.patch)).
- Nova owner reports the same symptom on a Retroid Pocket Nova ("accepts the thresholds but ignores them: they read back as 0"). [S] `msmirle/nova-charge-limiter@aa69f28:README.md#L21-L24, #L141`.

### Inferences
- A clean `0` rather than an errno means the GET itself succeeded with result 0 and value 0 (else the read would have failed). [U, derived from the source above]
- Three explanations fit every observation and the source cannot separate them: (a) the firmware ignores or never answers opcode 0x48 (the write then costs a 1 s timeout, silently), and property 26 is never populated; (b) the firmware accepts 0x48 but does not report property 26; (c) the firmware needs `BATT_CHG_CTRL_EN` set, as the QTI downstream driver does, and mainline never sets it. The missing `set_charging_limit` handler strings in the Thor firmware (Objective section) favour (a) or (b); that the downstream gate exists favours (c) being possible. [U]
- A quiet dmesg therefore proves nothing about the request. [U, derived from the absence of any log call]

### Gaps
- No kernel log, timing, or rpmsg trace of a threshold write on the Thor exists. Candidate experiments, none run: time the write (about 1.0 s would indicate `-ETIMEDOUT`); capture the firmware log during the write with `armada-charge-debug --ulog-only --watch 20` (it loads `pmic_pdcharger_ulog` and captures the `pmic_pdcharger_ulog_msg` tracepoint from `PMIC_LOGS_ADSP_APPS`, `refs/upstream/armada@574da80:system_files/usr/bin/armada-charge-debug#L125-L155`) and look for any message about the 0x48 request; read dmesg for `unknown message`. The same ulog channel is what exposed the charger firmware's state-machine cause in Armada issue #402 (secondary account by the reporter). [S] `refs/_gh/issues.json` issue 402 comment 2026-09-10T21:42.
- The Thor's `adsp_dtb.mbn` (16 184 bytes, vs 167 736 for a working Odin 3 build in issue #402) is the file that holds charger configuration in that case; whether anything threshold-related lives in the Thor's copy is unread. [S] issue 402 (reporter) for the role; sizes from `ls -la refs/upstream/armada/system_files/usr/lib/firmware/qcom/sm8550/ayn/thor/`.
- Badjowk (Odin 3 user) states that writing `charge_control_start_threshold` on a Thor "shuts off the screens until a hard reboot". Single unreproduced comment; treat as a hazard when experimenting. [S] `msmirle/nova-charge-limiter` issue 1, comment 2026-10-08T04:47Z ([link](https://github.com/msmirle/nova-charge-limiter/issues/1)).

## Q3. What do Armada's kernel patches say about charge control, thresholds, battmgr, and patch 0903?

### Takeaway
Armada carries four battmgr patches (0900-0903). Only 0903 touches charge control, and it does so by exposing the existing prop-10 current limit as `constant_charge_current`; it neither touches nor mentions the threshold path. The patch text gives one reason: bypass charging.

### Cited Findings
- 0903 (Armada-authored, no upstream) states: "The battery manager firmware takes a battery charge current limit (BATT_CHG_CTRL_LIM). Expose it as constant_charge_current on SM8550-class batteries. Writing 0 stops battery charging while the charger keeps powering the system from USB, which gives bypass charging." [V] `refs/upstream/armada@574da80:packages/kernel/patches/0903-power-supply-qcom-battmgr-expose-the-charge-current-limit.patch#L1-L8`; `packages/kernel/PATCHES.md#L397-L399` (`source: armada`, `upstream: local`).
- It adds `charge_current_limit(_max)` to the info struct, maps `CONSTANT_CHARGE_CURRENT(_MAX)` to props 10/11, a setter that rejects negatives and sends `BATTMGR_BAT_PROPERTY_SET` prop 10, `property_is_writeable`, and the SET-reply case described in Q2. [V] same patch `#L9-L120`.
- Introduced in commit `431bf57` (2026-09-24, author `virtudude`), whose message lists 0903 as "expose the battmgr charge current limit (0 = charger bypass)" inside an s2idle power-saving series. [V] `git -C refs/upstream/armada log -3 -- packages/kernel/patches/0903-…patch`.
- Sibling patches: 0900 logs USB type and adapter type (Armada diagnostic), 0901/0902 carry upstream submissions for `CHARGE_FULL*` and `CHARGE_NOW` ([lkml 10893](https://lkml.iu.edu/2608.3/10893.html), [10890](https://lkml.iu.edu/2608.3/10890.html)); 0503 (ROCKNIX) renames the supply to `battery`. [V] `refs/upstream/armada@574da80:packages/kernel/PATCHES.md#L386-L402`. `refs/upstream/armada-packages@f02c7c8` (archival, 2026-09-18) has 0900-0902 and no 0903.
- No Armada docs, DT or userspace in the clone mention `charge_control` or `charge_limit` apart from 0903's own text. [V] `rg -i 'charge_control|charge-limit|charge_limit|battmgr'` over `refs/upstream/armada@574da80` excluding patches/dts/firmware.
- DT: `qcs8550-ayn-common.dtsi` pmic-glink node has no nvmem cells (Q2); the Thor loads `qcom/sm8550/ayn/thor/adsp.mbn` + `adsp_dtb.mbn`. [V] `refs/upstream/armada@574da80:packages/kernel/dts/qcs8550-ayn-thor.dts#L457-L459`. The Thor firmware tree is carried in Armada's repo (`system_files/usr/lib/firmware/qcom/sm8550/ayn/thor/`, initial commit); the Arch port's PKGBUILD says it extracts the same files from ROCKNIX. [V] `refs/thor-linux/ayn-thor-arch@84aba0a:packages/linux-firmware-ayn-thor/PKGBUILD#L11-L36`. Where ROCKNIX got them is not stated in what was read.
- `battmgr.jsn` next to the blobs is only the pd-mapper service-registry entry for `msm/adsp/charger_pd`, not charger configuration. [V] `refs/upstream/armada@574da80:system_files/usr/lib/firmware/qcom/sm8550/ayn/thor/battmgr.jsn`.
- Armada's issue #363 "Battery charge limit to 80 %" is open with four comments from users; no maintainer reply, no mention of firmware thresholds. [V] `refs/_gh/issues.json` issue 363.
- Armada's only s2idle-aware charger-event code is the fan: patch 0532 registers `power_supply_reg_notifier` and reacts to `PSY_EVENT_PROP_CHANGED` while suspended, and its message states "This needs PWM and supply providers that keep working in suspend-to-idle" and "A power supply event that is never delivered leaves the fan as it was". [V] `refs/upstream/armada@574da80:packages/kernel/patches/0532-hwmon-pwm-fan-optionally-run-the-fan-while-charging-in-s2idle.patch#L10-L12, #L254-L258`.

### Inferences
- Patch 0903 was added for bypass charging, not as a replacement for the threshold feature; the authors do not say whether they tried the thresholds. [U]
- 0532 shows the pattern a kernel-side cap would use; it also shows that the same open question (does the supply driver emit events during s2idle?) is acknowledged but not answered in Armada's own text. [U]

### Gaps
- Why Armada chose the current-limit property over thresholds is not written anywhere found.
- Armada's Odin 3 and PS2 builds ship firmware with `battmgr_set_charging_limit`, yet no Armada patch or script exercises thresholds on them.

## Q4. How does AYN's Android implement "Stop at 80 %", and does the downstream qcom-battery driver talk to the same ADSP firmware?

### Takeaway
Android's `/sys/class/qcom-battery/` is the QTI `battery_chg`/`qti_battery_charger` class, which talks to the ADSP charger service over pmic_glink like mainline; AYN's `limit_capacity_charge` and `usb_charge_now` nodes are AYN additions whose driver source was not found. The firmware strings show AYN-specific cap logic inside the Thor's own ADSP blob, but the Linux property ID that drives it is only claimed by one fork.

### Cited Findings
- AYN's Android kernel loads `qti_battery_charger.ko`. [V] `refs/thor-android/android_device_ayn_qcs8550-common@d5e669d:modules/modules.load#L55`. The QTI driver registers its class as `qcom-battery`. [V] `NothingOSS/android_kernel_msm-6.1_nothing_sm7635@d5f5f96:drivers/power/supply/qti_battery_charger.c#L4415`. The Nothing driver's class attributes do not include `limit_capacity_charge`, `usb_charge_now` or `charging_enabled` (`#L3930-L3955`); LineageOS uses `/sys/class/qcom-battery/charging_enabled` and AYN's overlay lists the same node in `ueventd`. [V] `refs/thor-android/android_device_ayn_qcs8550-common@d5e669d:common.mk#L192`, `init/ueventd.qcom.rc#L621`. So AYN's driver is customised and its source is not in `refs/`.
- Android's DT defines `qcom,pmic_glink` with `PMIC_RTR_ADSP_APPS` and `protection-domain = "tms/servreg", "msm/adsp/charger_pd"` and a `qcom,battery_charger` child; the Thor's display overlay references `&battery_charger`. [V] `refs/thor-android/android_kernel_ayn_qcs8550-devicetrees@9b2d195:qcom/kalama.dtsi#L3532-L3541`; `moorechip/display/display/kalama-sde-display-ayn-odin2-thor.dtsi#L343-L346`. Mainline's Armada DT uses the same `charger_pd` service through `qcom,sm8550-pmic-glink`; PDR on `msm/adsp/charger_pd` is what `qcom_battmgr` waits for. [V] `qcs8550-ayn-common.dtsi#L58-L59` and `torvalds/linux@6c377d19d4a5:drivers/power/supply/qcom_battmgr.c#L1598-L1606`. Same ADSP service is therefore verified; "same firmware blob" is not (Android's `adsp.mbn` was not compared byte for byte with Armada's). [U]
- The Thor's ADSP binary contains AYN/ODM-specific battery-manager code that mainline never references: `usb_charge_now`, `limit_capacity_charge`, `curr_cap_state`/`last_cap_state` in `…qbg_r1_charger_config`; `battmngr_enable_battery_charge 0!/1!`; and in `battmngr_i.c` the debug strings `set fake_soh %d`, `set force_5v %d`, `set soh_protect %d` (the AYN dashboard documentation for the Odin 3 also lists `limit_capacity_charge` and `force_5v` nodes). [V] `refs/upstream/armada@574da80:system_files/usr/lib/firmware/qcom/sm8550/ayn/thor/adsp.mbn` offsets 0xc7358f, 0xc73674, 0xcc21f8, 0xcc2212; [S] [LeXwDeX/odin3-desktop docs/dashboard.md](https://github.com/LeXwDeX/odin3-desktop/blob/HEAD/docs/dashboard.md).
- The Odin 3 / PS2 / PFE blobs additionally log `battmngr_set_charging_limit::enable = %d, target soc = %d, delta soc = %d` and, in `battmngr_i.c`, `set limit_capacity %d`; the Odin 3 blob contains both the AYN `limit_capacity_charge` code and the generic limit handler, the Thor blob only the former. [V] offsets in the Objective section.
- MgeeeeK's patch 0921 says it routes SM8550 end-threshold writes to "AYN limit_capacity_charge" as pmic_glink property **16** (`BATT_AYN_LIMIT_CAPACITY`, value 1 for enable) and claims "Verified live on AYN Thor 2026-09-14: the firmware accepts SET property 16 (readback 1/0)". [S, low confidence] [raw patch](https://raw.githubusercontent.com/MgeeeeK/armada-packages/thor/kernel/patches/0921-power-supply-qcom-battmgr-ayn-limit-capacity.patch). Property 16 is `BATT_CHG_FULL_DESIGN` in both mainline and the QTI enum, and the fork's "readback" log prints `info.design_capacity`, which is where mainline stores property 16 GET replies. [V] `torvalds/linux@6c377d19d4a5:drivers/power/supply/qcom_battmgr.c#L66, #L1451-L1452`; `NothingOSS/…qti_battery_charger.c#L159-L186` (enum index 16). The fork never claims charging actually stopped at 80 %, and Armada's doc notes the fork's claims are unverified on hardware. [V] `docs/armada/forks-and-related.md#L96`.
- Android-side behaviour reported by an independent Thor user: the toggle holds charge at 80 %, does not discharge a fuller battery, and "Android still says charging". [S] `Charging.kt#L10-L16` (see Objective).

### Inferences
- Android's "Stop at 80 %" is most plausibly a one-bit command to the ADSP firmware (AYN driver writes `limit_capacity_charge`, firmware's `charger_config` applies it against `bat_capacity` with a capacity-state hysteresis) rather than polling in the kernel. This follows from the firmware strings plus the node names; the AP-side code was not read. [U]
- If property 16 really is the AYN toggle, it collides with the mainline meaning of 16 (`BATT_CHG_FULL_DESIGN`), which would make the fork's "readback 1/0" suspect or implies AYN repurposed the ID. Not resolvable from the sources read. [U]

### Gaps
- AYN's `qti_battery_charger` source (where `limit_capacity_charge` is implemented, and which property or opcode it sends) is not public in the clones; a disassembly of the Android module (as the Odin 3 reporter did for another opcode) would settle the ID.
- Whether the firmware's `limit_capacity_charge` threshold is exactly 80 % and whether it persists in PMIC SDAM (`battmngr_platform_set_charging_props_to_sdam` and several `…_to_sdam` helpers exist in the strings) is unknown.

## Q5. Do other Snapdragon devices report that firmware thresholds work and survive suspend?

### Takeaway
Evidence that firmware thresholds persist exists only for reboot, on X1E80100 laptops and an Odin 3, and the Odin 3 report is a secondary account. Nobody found reports that a threshold holds through suspend on any Snapdragon device. SM8550-class handhelds reported here (Thor, Nova) show thresholds ignored.

### Cited Findings
- X1E80100 CRD / ThinkPad T14s OLED: GNOME sets the properties and "they are correctly loaded back at reboot"; Fenglin Wu says the values live in nvmem and survive until the battery is unplugged or drained. [V, mailing-list text] Neil Armstrong [2025-09-03](https://lkml.iu.edu/hypermail/linux/kernel/2509.0/04320.html); Fenglin Wu [2025-11-17](https://lkml.iu.edu/2511.2/02578.html). Nothing in these threads tests suspend.
- Firmware-side enforcement on X1E80100: bit 8 of notification 0x83 means "charging stops because the charge control end threshold is reached". [V] [commit 41307ec](https://github.com/torvalds/linux/commit/41307ec7df057239aae3d0f089cc35a0d735cdf8).
- Val Packett reverted her own "disable" support because the disable bit "was acting rather strange". [V] [lkml 2511.0/01157](https://lkml.iu.edu/2511.0/01157.html).
- AYN Odin 3 under a custom Linux build showed `CHARGE_CONTROL_START_THRESHOLD=70`, `CHARGE_CONTROL_END_THRESHOLD=80` that the author labels "inherited from Android" (set by the Android side, read under Linux). [S] `arcadematicas/pocknix-odin3-support@14f4907:docs/BATTERY-ISSUE.md#L27-L28` ([raw](https://raw.githubusercontent.com/arcadematicas/pocknix-odin3-support/master/docs/BATTERY-ISSUE.md)). The same Odin 3 firmware family logs `battmngr_set_charging_limit` (Objective). A user also posted a 75/80 threshold script for the Odin 3 that "was basically all wired up already", with expected readbacks 75 and 80; this is a description of intended output, not a recorded result. [S] [msmirle/nova-charge-limiter issue 1](https://github.com/msmirle/nova-charge-limiter/issues/1).
- Retroid Pocket Nova: thresholds accepted, read back 0, ignored; a build that sent only the firmware threshold still let the battery climb from 69 % to 96 % while asleep; `constant_charge_current` = 0 held through sleep but needs fake suspend to be flipped at 80 %. [S] `nova-charge-limiter@aa69f28:README.md#L21-L24, #L141-L156` (the project says the Nova's firmware is "shared with the AYN Odin 2"; the Odin 2 blobs in Armada lack the `limit_capacity_charge` strings that the Thor and RP6 have, so that statement is not supported by the blobs in the tree, and the Nova's own blob is not in the tree). The README's deep-sleep-at-limit mode is described as untested on a Nova. [S] `#L103-L105`.
- Thor: thresholds ignored on stock Armada `20261006.9c7dd3e` (kernel 7.2.6); `constant_charge_current` clamp works and the Gleipnir cycle held through a game and a charger swap. [V, local] `docs/hardware/device-observed.md#L75, #L89-L99`.
- Armada issue #363 asks for an 80 % limit on Odin 3, Thor and Nova and is unanswered. [V] `refs/_gh/issues.json` issue 363.
- As of 2026-08-05 every SM8550 Armada device ran `ARMADA_SUSPEND_MODE=fake` (commit message of `ee66da0`), so the charger firmware was not exercised by a real s2idle there; the 2026-09-24 commit `431bf57` later reports s2idle sleep power measured on the Thor, and the current `device-env` defaults to s2idle with a fake-suspend fallback for some devices. [V] `git -C refs/upstream/armada show ee66da0`; `git show 431bf57`; `refs/upstream/armada@574da80:system_files/usr/libexec/armada/device-env#L56-L62` (which devices fall back to fake was not read).

### Inferences
- Persistence of the mainline thresholds is by design in firmware/SDAM on platforms that implement 0x48, which would make "survives suspend with no userspace" plausible there, but it is untested for suspend in every source found. [U]
- The Odin 3 / PS2 / PFE blobs implement the mainline handler while the Thor / RP6 / Odin 2 blobs do not, which lines up with the reports of working versus ignored thresholds. [U]

### Gaps
- No report found for Ayaneo, Retroid RP6, or postmarketOS devices showing a threshold surviving suspend; searches for GitHub issues, ROCKNIX and Armada returned nothing beyond the items above.
- ROCKNIX's `charge_behaviour` work (`ROCKNIX/distribution` PR 2840, SM8750 bypass via `USB_PROPERTY_SET` property 14) is an input-inhibit mechanism, open and unmerged; its suspend behaviour is not reported. [S] `gh pr view 2840 --repo ROCKNIX/distribution`.
- Odin 3 SM8750 thresholds were not measured for effect (does charging actually stop at 80 %?) in any source read.
