## 1. What happens on resume from an RTC (non-input) wake in s2idle: display, session, any "unexpected wake" handler, any existing use of wakealarm

### Takeaway
Nothing in the Armada tree distinguishes an RTC wake from a power-key wake, and nothing in the s2idle path turns the display on or puts the system back to sleep: the s2idle path is `systemd-sleep suspend` plus two hooks. No Armada code lights the panel on an s2idle resume; which component does (kernel DRM resume, gamescope, Steam) is unverified. Armada has no auto-re-sleep or "unexpected wake" handler. Armada at HEAD only reads `wakealarm` (debug report); an earlier Armada hook armed an off-by-default RTC "watchdog" but it is gone from HEAD.

### Inferences
- Because Armada has no wake-source discrimination, an RTC wake is processed like any other wake: kernel resume, `post` hooks (ledger line, USR1 to powerbuttond), logind `PrepareForSleep(false)`, powerd re-applies the profile, user.slice thaws. Which component turned the display on in the Thor tests is unverified; candidates are the kernel DRM resume (the historical hook's authors assumed this), gamescope, or Steam reacting to resume.
- Whether the Thor goes back to sleep after an RTC wake depends on things outside the Armada tree: Steam's own idle/suspend timer and any desktop-mode PowerDevil policy (neither read; Steam is closed source and no `powerdevil` config was found in `system_files`). A test that leaves the device idle on the lit screen would show it.
- A charge-cap daemon that uses RTC wakes would have to re-suspend itself (for example `systemctl suspend`, which re-runs `suspend-dispatch`). Between the wake and the re-suspend the panel is probably lit, so a visible flash is expected; this is inference, not observed.
- The wake ledger will show the RTC alarm IRQ by name on the next RTC wake; `/var/lib/armada/wake-ledger.log` on the device is the primary evidence for what woke each cycle.

### Gaps
- What actually turns the panel on after an RTC resume in s2idle (kernel msm DRM resume vs gamescope vs Steam). Needs an on-device log line, for example `bl_power`, the CRTC state and gamescope's `drm_sleep_internal_screen` value read right after an RTC wake.
- Whether Steam Game Mode re-suspends after a timer wake (idle-suspend setting): closed source, not in the clones.
- Hooks on the device, not the repo: `/etc/systemd/system-sleep/` and the sleep-debug drop-in `/etc/systemd/system/systemd-suspend.service.d/90-armada-sleep-debug.conf` (path from `system.py` L16, not read) were not inspected. Per the project notes, charge-limiter units existed in `/etc` before the 2026-10-07 reset, so the repo's "only two hooks" is a statement about the clone only.
- The commit that removed `50-armada-real-suspend`, and why (not identified).
- Any PowerDevil idle policy in desktop mode (not looked up).
- Decisive on-device check for "does anything re-suspend after a non-input wake": in `/var/lib/armada/wake-ledger.log`, look at the IRQ 199 `Sensor` wakes (assignment) and the RTC test wakes. If a wake entry is followed by another ledger entry with no power-key wake between them, something suspended the device again without the user; the journal's logind suspend lines for that window show who asked. Unverified caveat that matters here: Steam's sleep-on-idle timer may be set differently when plugged in, and plugged in is exactly the charge-cap case.
- Steam Deck / Steam forum reports of RTC wakes lighting the screen: none found with one web search.

## 2. Fake suspend: what is frozen, what keeps running, CPU idle, power cost, and what the "Sleep type" toggle changes

### Takeaway
Fake suspend freezes only the session user's `app.slice` cgroup (Steam, games, anything under it). Every system service in `system.slice` (including Armada's own `armada-powerd`, NetworkManager, and any root service you add) keeps running, the kernel stays fully awake, and Wi-Fi/Bluetooth stay up. The Sleep type toggle writes `suspend_mode=` to `/etc/armada/sleep.conf`.

### Cited Findings
- Header: real suspend "hangs this SoC"; `fake-suspend` runs as `systemd-suspend.service` and blocks until woken, so logind's sleep lifecycle lasts the whole sleep. [refs/upstream/armada@574da80:system_files/usr/libexec/armada/fake-suspend#L1-3](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/fake-suspend) **[V]**
- Entering (`do_suspend`), in order: touch state flag `/run/armada/fake-suspend.active`, mute the default sink, find the power-key device, grab every input device except the lid switch and the power-key reader with `evtest --grab`, display off, freeze processes, call `armada-power suspend` (timeout 10 s; aborts the fake suspend on failure), then runtime-PM changes. [refs/upstream/armada@574da80:system_files/usr/libexec/armada/fake-suspend#L152-163, L263-281](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/fake-suspend) **[V]**
- Display off: `gamescopectl drm_sleep_internal_screen 1` against every `gamescope-N` socket in the session runtime dir, falling back to `bl_power=4`. [refs/upstream/armada@574da80:system_files/usr/libexec/armada/fake-suspend#L53-68](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/fake-suspend) **[V]**
- Freeze: asks the session user's manager for `app.slice`'s cgroup path (`systemctl --user show app.slice -P ControlGroup`) and writes `1` to its `cgroup.freeze`. If that fails, fallback: `SIGSTOP` every process in the gamescope cgroup except comms `gamescope-wl|gamescope-sessi|Xwayland|mangoapp|steam_notif_dae`. Unfreeze reverses it (and ends with `kill -CONT -1`). [refs/upstream/armada@574da80:system_files/usr/libexec/armada/fake-suspend#L209-261](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/fake-suspend) **[V]**
- Not frozen by this code: anything outside the session user's `app.slice`, namely `system.slice` services, `session.slice` (PR #127 says pipewire/wireplumber run in a sibling cgroup `session.slice` and were deliberately left running; the older code froze all of `user.slice`), kernel threads, and `fake-suspend` itself. [PR #127](https://github.com/armada-os/armada/pull/127) **[V]** for the quote, **[S]** for the cgroup layout on the Thor.
- Direct code evidence that a system-slice daemon keeps running: `armada-powerd` (a system service, `Type=dbus`) has a `GLib.timeout_add_seconds(3, self.fan_tick)` loop, and `fan_tick` has an explicit `if self.suspended:` branch (flag set by `suspend()`, which the D-Bus `Suspend` method calls at L1041-1042; `armada-power suspend` invokes that method) that keeps adjusting the fan during fake sleep. [refs/upstream/armada@574da80:system_files/usr/libexec/armada/armada-powerd#L270, L688-714, L839-882, L1041-1046](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/armada-powerd) [refs/upstream/armada@574da80:system_files/usr/bin/armada-power#L121-126](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/bin/armada-power) [refs/upstream/armada@574da80:system_files/usr/lib/systemd/system/armada-powerd.service#L1-17](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/lib/systemd/system/armada-powerd.service) **[V]**
- The cgroup freezer applies to "the cgroup and all descendant cgroups"; frozen processes can still be killed by fatal signals. [cgroup-v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) **[S]**
- CPU: the kernel is running, not suspended. `armada-power suspend` makes `armada-powerd.suspend()` write the lowest available frequency to every cpufreq policy's `scaling_min_freq` and `scaling_max_freq` and the lowest GPU devfreq to `min_freq`/`max_freq`; `resume()` restores saved values. [refs/upstream/armada@574da80:system_files/usr/libexec/armada/armada-powerd#L688-748](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/armada-powerd) **[V]** Whether the CPUs reach deep idle states during fake sleep was not measured: **[U]**.
- Runtime PM: only `/sys/devices/platform/soc@0/*.usb` get `power/control=auto`; the comment says GPU runtime PM is left alone because "the GMU is known to wedge under rapid idle/resume churn". - Related kernel-side precedent: Armada kernel patch 0532 adds `pwm1_sleep_charging` so the fan can keep running during s2idle on external power ("The fan is always stopped at suspend, so a handheld charging while asleep heats up with no airflow"). `armada-powerd` writes it from `[fan] charging_pwm` (default 0). [refs/upstream/armada@574da80:packages/kernel/patches/0532-hwmon-pwm-fan-optionally-run-the-fan-while-charging-in-s2idle.patch#L1-20](G:/Projects/Hardware/AynThor/refs/upstream/armada/packages/kernel/patches/0532-hwmon-pwm-fan-optionally-run-the-fan-while-charging-in-s2idle.patch) [refs/upstream/armada@574da80:system_files/usr/libexec/armada/armada-powerd#L830-837](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/armada-powerd) [refs/upstream/armada@574da80:system_files/usr/share/armada/power-profiles.conf#L43-50](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/share/armada/power-profiles.conf) **[V]**

### Inferences
- A root systemd service (system.slice) is not touched by fake suspend, so a charge-cap daemon keeps polling and writing sysfs during fake sleep exactly as when awake, with no RTC wake needed. `armada-powerd`'s 3 s timer working in its `suspended` branch is the in-tree precedent.
- A service can learn the state via logind `PrepareForSleep` (as powerd does) or `/run/armada/fake-suspend.active`. Waking a fake-suspended device means writing `/run/armada/fake-suspend.wake`, which also lights the display, so it is not suitable for a silent cap.
- Because radios are not blocked in fake mode, Wi-Fi and Bluetooth stay up and should drain more than s2idle; consistent with the docs, but no measured number exists in the sources.

### Gaps
- Measured idle drain of fake vs s2idle on the Thor (SM8550): no figure in docs or issues.
- Whether CPUs reach deep cpuidle states in fake mode.
- Which cgroup the Thor's `gamescope-session-plus@` and Steam actually sit in (app.slice vs session.slice) was not checked on the device; `cat /proc/<gamescope pid>/cgroup` would show it.
- Whether `/etc/armada/sleep.conf` exists on the Thor and its current content (the assignment says s2idle is confirmed on device; the file itself was not read).

## 3. s2idle: are all userspace processes (including system.slice services) frozen?

### Takeaway
Yes. In s2idle the kernel freezes all freezable userspace tasks, system-wide and not per-cgroup, so a system.slice daemon does not run between the write to `/sys/power/state` and the wake; only wake-capable interrupts and kernel context run.

### Cited Findings
- Kernel sleep-states doc: s2idle works by "freezing user space, suspending the timekeeping and putting all I/O devices into low-power states"; CPUs can spend time in their deepest idle states; wake is by in-band interrupts; `s2idle` is always available with `CONFIG_SUSPEND`. [kernel: sleep-states](https://docs.kernel.org/admin-guide/pm/sleep-states.html) **[S]** (WebFetch summary with quoted fragments)
- To enter s2idle: write `freeze` to `/sys/power/state`, or `s2idle` to `mem_sleep` then `mem` to `state`. [kernel: sleep-states](https://docs.kernel.org/admin-guide/pm/sleep-states.html) **[S]**; `suspend-dispatch` does the second form. [refs/upstream/armada@574da80:system_files/usr/libexec/armada/suspend-dispatch#L19-37](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/suspend-dispatch) **[V]**
- Freezer doc: user space processes and some kernel threads are frozen during system-wide suspend; tasks are "freezable" unless flagged; kernel threads are not freezable by default and become so only via `set_freezable()`. Reasons given: filesystem consistency, memory, and keeping tasks from touching devices while they suspend. [kernel: freezing-of-tasks](https://docs.kernel.org/power/freezing-of-tasks.html) **[S]**
- systemd additionally freezes `user.slice` itself around the hooks (section 5). [systemd-suspend.service(8)](https://man7.org/linux/man-pages/man8/systemd-suspend.service.8.html) **[S]**; `sleep.c` `verb_operate()` uses `unit_freezer_new(SPECIAL_USER_SLICE)` unless `SYSTEMD_SLEEP_FREEZE_USER_SESSIONS=0`. [sleep.c](https://raw.githubusercontent.com/systemd/systemd/main/src/sleep/sleep.c) **[S]** (WebFetch summary of raw source)
- `rtcwake -m freeze` is documented as "Freezes processes, suspends devices, and idles processors." [rtcwake(8)](https://man7.org/linux/man-pages/man8/rtcwake.8.html) **[S]**
- Armada's pwm-fan patch 0532 says "The fan is always stopped at suspend" and that "PWM and supply providers must keep working in s2idle", and reacts to charger changes with a power-supply notifier in kernel context. [refs/upstream/armada@574da80:packages/kernel/patches/0532-hwmon-pwm-fan-optionally-run-the-fan-while-charging-in-s2idle.patch#L1-20, L318](G:/Projects/Hardware/AynThor/refs/upstream/armada/packages/kernel/patches/0532-hwmon-pwm-fan-optionally-run-the-fan-while-charging-in-s2idle.patch) **[V]** (the patch does not give userspace freezing as its reason; see Inferences)
- `armada-powerd.service` is an ordinary system service (`Type=dbus`, `WatchdogSec=15`, `Restart=always`); nothing exempts it from the freezer. [refs/upstream/armada@574da80:system_files/usr/lib/systemd/system/armada-powerd.service#L1-17](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/lib/systemd/system/armada-powerd.service) **[V]**

### Inferences
- Armada did its "act during s2idle" work for the fan in the kernel (patch 0532); a plausible reason is that userspace is frozen, but the patch does not say so, so this is inference.
- With kernel-wide freezing, no system.slice service (a root charge-cap daemon, or `armada-powerd`'s fan loop) runs while the SoC is in s2idle.
- Any userspace action needed for the cap must happen in a `pre` hook (before the write to `/sys/power/state`), or be enforced by hardware/firmware/kernel (for example a charge-control threshold), or the daemon needs an RTC wake to run at all (section 4).
- Powerd has `WatchdogSec=15`; I did not verify how systemd's watchdog timing behaves across a long s2idle **[U]**.

### Gaps
- The kernel page fetched says s2idle wakes are "in-band interrupts" and does not mention the RTC. The working RTC freeze tests (assignment) are empirical, not documented here.
- Whether the Thor's charger/PMIC keeps enforcing a previously written charge limit through s2idle was not examined (other researchers' scope).

## 5. systemd-sleep hook execution environment

### Takeaway
Hooks in `/usr/lib/systemd/system-sleep/` are run by `systemd-sleep` inside the root `systemd-suspend.service`, all in parallel and with errors ignored, called with `pre`/`post` and the action (`suspend`) around the kernel write. `user.slice` is frozen while they run. They can delay but not veto the suspend or resume.

### Cited Findings
- Hooks run "immediately before entering suspend" with first argument `pre` and again after resume with `post`; the second argument is the action (`suspend`, ...); `SYSTEMD_SLEEP_ACTION` is set; "All executables in this directory are executed in parallel" and the action does not continue until all finish; `user.slice` is frozen while they run so they should not wait on user services; the hooks "should be considered hacks" and inhibitor locks are preferred. [systemd-suspend.service(8)](https://man7.org/linux/man-pages/man8/systemd-suspend.service.8.html) **[S]** (WebFetch summary; the page does not state timeout or failure semantics)
- From `sleep.c` (WebFetch of the raw source): `execute()` opens `/sys/power/state`, optionally writes `mem_sleep`, sets `SYSTEMD_SLEEP_ACTION`, runs `pre` hooks via `execute_directories("system-sleep", ..., DEFAULT_TIMEOUT_USEC, ...)` with flags `EXEC_DIR_PARALLEL | EXEC_DIR_IGNORE_ERRORS`, calls `write_state()`, then runs `post` hooks unconditionally (even if the write failed). `user.slice` is frozen in `verb_operate()` before `execute()` and thawed after it returns. [sleep.c](https://raw.githubusercontent.com/systemd/systemd/main/src/sleep/sleep.c) **[S]**
- `DEFAULT_TIMEOUT_USEC` is defined as `(DEFAULT_TIMEOUT_SEC*USEC_PER_SEC)` in systemd `src/basic/constants.h` [constants.h](https://raw.githubusercontent.com/systemd/systemd/main/src/basic/constants.h) **[S]**; the numeric value of `DEFAULT_TIMEOUT_SEC` was not found in the fetched excerpt, so the hook timeout in seconds is **[U]**. Armada's drop-in sets `TimeoutStartSec=infinity` on the service, which governs service start, not necessarily each hook's own timeout. [refs/upstream/armada@574da80:system_files/usr/lib/systemd/system/systemd-suspend.service.d/10-armada-suspend.conf#L5-8](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/lib/systemd/system/systemd-suspend.service.d/10-armada-suspend.conf) **[V]**
- Execution identity: the hooks behave as root. Armada's hook writes sysfs `power/wakeup`, runs `id -u`, and sends `kill -USR1` to a process owned by the session user; `fake-suspend` uses `runuser -u armada` to drop to the session user. [refs/upstream/armada@574da80:system_files/usr/lib/systemd/system-sleep/50-armada-powerbutton-suspend#L16, L62, L94](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/lib/systemd/system-sleep/50-armada-powerbutton-suspend) [refs/upstream/armada@574da80:system_files/usr/libexec/armada/fake-suspend#L19-28](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/fake-suspend) **[V]** (that the service itself runs as root is **[S]**: inferred from the unit structure and this usage)
- Armada's own hooks are defensive about this environment: the sleep-debug hook wraps its work in `timeout --kill-after=1s 8s` and offloads reporting to `systemd-run --no-block`. [refs/upstream/armada@574da80:decky/armada-control/py_modules/armada_control/sleep_debug_hook.sh#L14-27](G:/Projects/Hardware/AynThor/refs/upstream/armada/decky/armada-control/py_modules/armada_control/sleep_debug_hook.sh) **[V]**
- Order for a plain suspend: freeze `user.slice` -> `pre` hooks (parallel) -> write `/sys/power/state` (kernel freezes the remaining userspace; system sleeps) -> wake -> `post` hooks (parallel) -> thaw `user.slice`. [sleep.c](https://raw.githubusercontent.com/systemd/systemd/main/src/sleep/sleep.c) **[S]**; consistent with Armada's comment that `user.slice` is frozen during `post` ([refs/upstream/armada@574da80:system_files/usr/lib/systemd/system-sleep/50-armada-powerbutton-suspend#L74](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/lib/systemd/system-sleep/50-armada-powerbutton-suspend)) **[V]**.
- In fake mode `suspend-dispatch` does not call `systemd-sleep`, so no system-sleep hooks run at all; `50-armada-powerbutton-suspend` also exits explicitly in its `post` branch when the mode is `fake`. [refs/upstream/armada@574da80:system_files/usr/libexec/armada/suspend-dispatch#L10-12](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/libexec/armada/suspend-dispatch) [refs/upstream/armada@574da80:system_files/usr/lib/systemd/system-sleep/50-armada-powerbutton-suspend#L75-76](G:/Projects/Hardware/AynThor/refs/upstream/armada/system_files/usr/lib/systemd/system-sleep/50-armada-powerbutton-suspend) **[V]**

### Inferences
- A `pre` hook that sets the charge cap runs as root with a live system.slice, but `user.slice` is already frozen, so it must not wait on user-session services (user D-Bus, Steam, Decky).
- Hook failure or slowness cannot cancel the suspend (errors are ignored); a hung hook delays suspend/resume until its timeout, whose value is not confirmed. Keep hooks short and wrap work in `timeout`.
- Hooks do not run in fake mode, so a cap implemented in a system-sleep hook only works for s2idle; a standing system service covers fake mode (section 2).
- `post` hooks run on every resume including RTC wakes, in parallel and while `user.slice` is still frozen, so a hook could detect an RTC wake (compare `/sys/power/pm_wakeup_irq`, as the ledger does) before the session thaws. This follows from the cited ordering and was not tested.

### Gaps
- The numeric hook timeout (`DEFAULT_TIMEOUT_SEC`) and behaviour when a hook exceeds it.
- Whether the systemd on the Thor's image includes the `user.slice` freeze (the man page and Armada's hook comment agree; the installed systemd version was not checked).
- The official freedesktop.org man page fetch was blocked (HTTP 403); the man7.org rendering was used instead.
